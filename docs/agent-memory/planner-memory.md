## 初始约定

- 默认先定义范围与验收标准，再进入编码阶段。
- 复杂需求先拆分为可并行任务，再分派给 coder / tester。
- tester 的反馈必须回写到计划文档中。

### 2026-05-05 - 个人网站首轮开发指派（画廊 + 记录）

- 背景：用户要求先不做 issue 间自动流转，由主 agent 直接指派 planner/coder/tester 并启动个人网站开发。
- 关键决策：首轮仅做前端静态可见成果，避免后端依赖阻塞交付；以“首页双入口 + notes 导航 + 内容样例 + E2E 回归”作为最小闭环。
- 设计/需求原则：复用既有深色玻璃视觉，不破坏主页地图与现有布局；保留 `#workflow-test` 作为流程验收锚点。
- 对 coder 的具体约束：集中修改首页入口区、导航高亮逻辑、notes markdown 内容与对应 E2E 断言，不扩展到 API/存储层。
- 对 tester 的验收重点：验证双入口可达、notes 导航在列表与详情均高亮、notes 列表/详情可用、全量 Playwright 回归通过。
- 后续待办：第二轮再推进上传流程细化（EXIF/元数据编辑）与画廊数据动态化能力。

### 2026-05-06 - 第二轮收尾与第三轮切入（部署稳定性优先）

- 背景：用户反馈 Cloudflare 自动部署在 `npx wrangler versions upload` 阶段报错，要求先修复构建链路，再继续第三轮开发并确保测试截图可见。
- 关键决策：先修复部署基础设施（`wrangler.jsonc` + assets/build command），再进行功能迭代，避免“功能完成但无法发布”的无效交付。
- 设计/需求原则：第三轮先做上传侧“可编辑元数据”闭环（标题、位置、标签、时间、设备、经纬度），并继续保持前端无后端依赖。
- 对 coder 的具体约束：上传页编辑能力必须与 discovery 同步数据打通，viewer 信息区继续复用；不得引入后端 API。
- 对 tester 的验收重点：覆盖 deploy dry-run、15 条 E2E 全量回归、截图产物路径可导出并可追踪。
- 后续待办：下一轮可进入批量编辑与地图聚合视图，并评估接入真实存储/API 的技术切换点。

### 2026-05-05 - 个人网站第二轮开发指派（上传元信息闭环）

- 背景：用户要求继续第二轮开发，重点贴合“上传后可展示参数、设备、地理位置”。
- 关键决策：坚持前端可交付路线，引入本地媒体元数据模型与本地存储同步，避免后端依赖阻塞。
- 设计/需求原则：上传页负责采集与元信息抽取，探索页/查看器负责消费展示；缺失元数据统一兜底为 `--`。
- 对 coder 的具体约束：实现上传队列（图片+视频）/EXIF 解析/探索页动态注入/查看器三分区信息展示，并补充对应 E2E。
- 对 tester 的验收重点：验证“不支持格式提示、元数据展示、无位置兜底、同步到探索页后查看器信息区可见”，并确保全量回归通过。
- 后续待办：若进入第三轮，可把本地存储数据切换为服务端 API 与持久化存储。
